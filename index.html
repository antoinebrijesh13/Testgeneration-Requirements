TestGeneration Pipeline Requirements

Goal

Automated program repair runs on tests. Most bug fixes ship with one, or none at all.

This system takes a bug and writes two kinds of tests for it: tests that catch the bug, and tests that guard the behaviour that already worked.

Together they give a repair tool enough to build a patch: the first kind proves the bug is gone, the second proves nothing else broke.

Scope

The system generates tests that catch the bug and tests that guard the behaviour that already worked.

It does not generate patches, judge whether a patch is correct, or choose which bugs to work on. A user takes the valid tests and runs them with a separate repair tool.

Definitions

  • bug — a defect that already has a fix.
  • buggy version — the code before the fix.
  • fixed version — the code after the fix.
  • failing test — the test that already exists and fails on the buggy version.
  • broken code — the file, line and method where the failure happened.
  • evidence — what the system recorded about a bug: the broken code and the error the failing test reported.
  • negative test — a test that fails on the buggy version and passes on the fixed version.
  • positive test — a test that passes on both versions.
  • candidate test — a test that has been written but not yet accepted or rejected.
  • valid test — a candidate test that met every check and was kept.
  • coverage — a record of which lines ran while a test was running.
  • environment — the Python installation a project's tests run under.
  • repair tool (PyTER) — a separate program that fixes the buggy code using the generated positive and negative tests.

Dependencies

  • a language model — writes each candidate test when the system asks for one
  • a bug benchmark — supplies each bug: both versions of the code and a test that already fails
  • the project's environment — the Python installation the tests run under; it must have pytest and coverage
  • a user — selects the bug to work on, then takes the valid tests to the repair tool

System Requirements

SYS-01
The system shall identify the buggy version, the fixed version, the failing test and the environment for a bug.
Met by CTX-01, CTX-02
SYS-02
The system shall stop and report which input is missing when the buggy version, fixed version, failing test or environment cannot be found or run.
Met by CTX-03
SYS-03
The system shall record the evidence for a bug.
Met by EVD-01, EVD-02, EVD-03, EVD-04
SYS-04
The system shall write every candidate test from that evidence.
Met by BEN-01, BEN-02, BEN-03, GDE-01, GDE-02, GEN-01
SYS-05
The system shall write both negative tests and positive tests.
Met by GDE-03, GEN-02, GEN-03, GEN-04
SYS-06
The system shall give the reason why an earlier candidate test was rejected when asking for another candidate test for the same bug.
Met by LOP-01
SYS-07
The system shall run every candidate test on the buggy version and on the fixed version.
Met by RUN-01, RUN-02
SYS-08
The system shall use coverage to check whether a candidate test reached the broken code.
Met by REL-01, REL-02, REL-03
SYS-09
The system shall accept a candidate test only if it behaves as a negative test or a positive test.
Met by ACC-01, ACC-03, ACC-04
SYS-10
The system shall accept a negative test only if it fails with the error recorded in the evidence.
Met by ACC-02
SYS-11
The system shall record the reason a candidate test was rejected.
Met by ACC-05
SYS-12
The system shall limit how long a single candidate test may run.
Met by RUN-03
SYS-13
The system shall limit how many candidate tests it writes for one bug.
Met by LOP-02, LOP-03, LOP-04
SYS-14
The system shall record the outcome of every candidate test.
Met by OUT-01, OUT-02, OUT-03
SYS-15
The system shall save the valid tests for each bug in a directory of their own.
Met by OUT-04
SYS-16
The system shall save, with each valid test, the settings and evidence it came from.
Met by OUT-05

The validation module shall run each candidate test on the fixed checkout and save the result.

Relevance

REL-01
The validation module shall collect coverage while the test runs.
Serves SYS-08 · validate_tests.py: run_pytest_with_coverage
REL-02
The validation module shall check whether the broken line or the broken method was reached.
Serves SYS-08 · validate_tests.py: validate_negative / validate_positive
REL-03
The validation module shall record which evidence was used: exact line, method, or traceback text.
Serves SYS-08 · validate_tests.py: output_mentions_fault_line

Acceptance

ACC-01
A bug-catching test shall be accepted only if it fails on the buggy code and passes on the fixed code.
Serves SYS-09 · validate_tests.py: validate_negative
ACC-02
A bug-catching test shall be accepted only if its failure matches the recorded failure.
Serves SYS-10 · validate_tests.py: benchmark_error_signature / _msgs_match
ACC-03
A behaviour test shall be accepted only if it passes on both versions.
Serves SYS-09 · validate_tests.py: validate_positive
ACC-04
A test shall be accepted only if it also passed the relevance check.
Serves SYS-09 · iterative_generation.py: AcceptanceCriteria
ACC-05
The validation module shall record the reason for every rejection.
Serves SYS-11 · iterative_generation.py: FailureRecord

Loop

LOP-01

Serves SYS-13 · iterative_generation.py: iterate, target 5
LOP-03
The controller shall stop when the try limit is reached.
Serves SYS-13 · iterative_generation.py: iterate, 15 attempts
LOP-04
The controller shall stop when the same rejection reason repeats too many times.
Serves SYS-13 · iterative_generation.py: iterate, streak limit 3
