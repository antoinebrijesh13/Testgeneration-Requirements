TestGeneration Pipeline Requirements

Goal

The goal of the system is to generate positive and negative tests that improve the quality of patches generated by a repair tool.

Dependencies and inputs

  • User: selects the project, bug, and variant where applicable, and supplies run settings.
  • Bug benchmark: supplies the buggy and fixed source versions and the original failing tests.
  • Project environment: supplies the runtime, project dependencies, test runner, and coverage collection needed to execute the tests.
  • Language model: produces candidate tests from the supplied bug evidence.
  • Repair tool: accepts the buggy code and valid tests and returns candidate patches or an execution outcome.

FR-01 — Identify and prepare the bug

The system shall identify and verify the buggy version, fixed version, original failing tests, and execution environment associated with the selected bug before generating tests.

Details
  • FR-01.01: The system shall accept a project identifier, bug identifier, and, where required, variant identifier that together select one bug instance.
  • FR-01.02: The system shall record the locations and source revisions or content fingerprints of the selected buggy and fixed versions.
  • FR-01.03: The system shall record the identifiers, source, and execution commands of the original failing tests associated with that bug instance.
  • FR-01.04: The system shall record the environment and execution configuration used for each version, including the interpreter and dependency versions.
  • FR-01.05: The system shall execute each selected original failing test on both versions and record the outcome of each execution.
  • FR-01.06: The system shall permit test generation only when every selected original failing test produces FAIL on the buggy version and PASS on the fixed version.
  • FR-01.07: The system shall record the observed failure evidence, identified fault location, target function or method, and corresponding source location in the fixed version.
  • FR-01.08: If a required input is unavailable, a required source location cannot be identified, or the original failure cannot be reproduced as required by FR-01.06, the system shall stop processing that bug and report the missing input or failed check.

Verification example: Select a known bug and inspect the recorded versions, environment, and FAIL/PASS results. Repeat with a missing interpreter and with an original test that passes on the buggy version; neither case may proceed to generation.

FR-02 — Generate positive and negative candidate tests

The system shall generate positive and negative candidate tests for the selected bug using its recorded source and failure evidence.

Details
  • FR-02.01: The system shall accept a target number of valid tests and a maximum number of generation attempts separately for positive and negative tests; each value shall be a positive integer.
  • FR-02.02: The system shall provide the generation process with the selected bug's original failing tests, required test helpers, relevant source code, failure evidence, and intended test type.
  • FR-02.03: The system shall request positive candidates that check specified behaviour of the target function or method expected to pass on both versions.
  • FR-02.04: The system shall request negative candidates that check the intended corrected behaviour and are expected to fail on the buggy version because of the selected bug.
  • FR-02.05: The system shall record each candidate's identifier, bug identifier, intended type, executable test code, expected behaviour, and generation settings.
  • FR-02.06: The system shall record a generation error for a response missing required candidate information and count that attempt toward the configured limit.
  • FR-02.07: The system shall submit every complete candidate to FR-03 before counting it toward the valid-test target.
  • FR-02.08: When another attempt is made after rejection, the system shall provide the generation process with the rejected candidate's code, execution results, and rejection reasons for that bug and test type.
  • FR-02.09: The system shall stop generating a test type when its valid-test target is reached or its attempt limit is reached, whichever occurs first.
  • FR-02.10: The system shall record the number of attempts, accepted tests, rejected tests, generation errors, and the stopping reason for each test type, identifying any unmet target.

Verification example: Request two valid tests of each type with a three-attempt limit per type. Check that accepted counts determine completion, invalid responses consume attempts, and a type with fewer than two accepted tests is reported as incomplete.

FR-03 — Validate generated candidate tests

The system shall accept a generated candidate test only when execution on the buggy and fixed versions satisfies the acceptance conditions for its declared type.

Details
  • FR-03.01: The system shall execute the same candidate test code against each recorded version using the corresponding environment and restored initial test state.
  • FR-03.02: The system shall record each execution's outcome, test-runner output, source version, environment, and evidence of the source locations executed.
  • FR-03.03: The system shall stop a candidate execution that exceeds the configured time limit and record TIMEOUT.
  • FR-03.04: The system shall accept a positive candidate if and only if it produces PASS on both versions and coverage evidence shows execution of the target function or method on both versions.
  • FR-03.05: The system shall accept a negative candidate if and only if all of the following hold: it produces FAIL on the buggy version, produces PASS on the fixed version, reaches the buggy fault location, executes the corresponding fixed location or containing function or method, and satisfies the recorded failure-matching rule.
  • FR-03.06: The system shall record whether negative-test relevance was established by line coverage, function or method coverage on the fixed version, or a traceback identifying the buggy fault location.
  • FR-03.07: Before accepting negative candidates, the system shall record an executable failure-matching rule derived from the original failure. The rule shall specify the exception or assertion category, the compared message or observed-value fields, and every permitted normalization or variable-field exclusion. Missing evidence shall produce an unmet check rather than an automatic match.
  • FR-03.08: The system shall reject a candidate if either execution produces ERROR, TIMEOUT, or NOT EXECUTED, or if any acceptance condition for its declared type is unmet.
  • FR-03.09: The system shall record each candidate's acceptance decision and the evidence for every applicable check, including each rejection reason.
  • FR-03.10: The system shall save accepted test code with its validation record and use only that validated code in the repair stage; changed test code shall require revalidation.

The execution matrix below is necessary but not sufficient: relevance and failure matching still apply.

Declared type Buggy version Fixed version Decision from execution outcomes
Positive PASS PASS Eligible if the positive relevance checks also pass
Negative FAIL PASS Eligible if the negative relevance and failure-matching checks also pass
Either Any other combination Reject

Verification example: Supply a relevant PASS/PASS positive, a matching FAIL/PASS negative, an unrelated FAIL/PASS candidate, a skipped test, and a test with a missing dependency. Only the first two may be accepted. A positive candidate with FAIL/PASS results is rejected as a positive; it is not silently relabelled.

FR-04 — Generate candidate patches using validated tests

The system shall invoke the selected repair tool on the buggy version using the validated positive and negative tests and collect the candidate patches returned by the tool.

Details
  • FR-04.01: The system shall accept the repair-tool identifier, invocation settings, and execution time limit for the repair run.
  • FR-04.02: The system shall start repair only when at least one valid positive test and one valid negative test are available for the same bug instance and recorded versions.
  • FR-04.03: If FR-04.02 is unmet, the system shall record that repair was not started and identify the missing test type.
  • FR-04.04: The system shall supply a copy of the buggy version and the accepted positive and negative tests to the repair tool, preserving their identities and executable behaviour during any required input-format conversion.
  • FR-04.05: The system shall record the exact test set, original failing tests if supplied, repair-tool version, settings, and source snapshot used for the invocation.
  • FR-04.06: The system shall invoke the tool and record its completion status and output, distinguishing returned patches, completion without a patch, execution error, and timeout.
  • FR-04.07: The system shall terminate a repair invocation that exceeds its configured time limit and retain any complete patches already returned.
  • FR-04.08: The system shall save each returned candidate patch with an identifier linking it to the bug, repair invocation, and test inputs, and provide its saved location to the user for manual evaluation.
  • FR-04.09: The system shall produce a run report identifying generated-test counts, repair status, returned patch identifiers and locations, and incomplete stages.

Verification example: Use a repair-tool stub that captures its inputs and returns two patches. Confirm that it receives only accepted generated tests from the selected bug and that both patches are saved with their identifiers and locations in the run report. Repeat with no valid negative tests and verify that the tool is not invoked.

FR-05 — Evaluate candidate patches using developer tests

Performed manually by the user after FR-04. This requirement describes the evaluation activity in the overall workflow; it does not require the system to automate patch evaluation.

The user shall evaluate each candidate patch by running the developer test suite against the patched version and recording whether all tests pass or any test fails.

Details
  • FR-05.01: The user shall evaluate each candidate patch separately on a copy of the corresponding buggy version with that patch applied; a patched version supplied by the repair tool may be used directly.
  • FR-05.02: The user shall run the developer test suite against the patched version using the project's test environment.
  • FR-05.03: The user shall record the patch as passing this evaluation if all tests pass, or failing this evaluation if any test fails, and associate the result with the evaluated patch.
  • FR-05.04: If no test failure is observed but execution cannot complete or tests do not execute, the user shall record the evaluation as incomplete rather than passing.

Passing the suite demonstrates that the patch satisfies those tests; it does not prove correctness for untested behaviour.

Verification example: Manually run the developer test suite on two candidate patches. Record a passing result for a patch on which all tests pass and a failing result for a patch on which at least one test fails.

Definitions

Term Meaning
Bug A problem in the program that causes it to behave incorrectly. In this project, each selected bug has an existing developer fix.
Buggy version The program's code before the developer fixed the selected bug.
Fixed version The program's code after the developer fixed the selected bug. The system uses this version to check generated tests.
Original failing test An existing test written by a developer that fails on the buggy version because of the selected bug.
Coverage A record of the lines of code that ran during a test.
Environment The software, settings, and resources needed to run the project's tests, including Python, required libraries, and the test runner.
Failure evidence Information recorded when the original failing test fails, such as the error message and where the failure occurred.
Fault location The file and line of code identified for the selected bug.
Target function or method The function or method that the generated tests are intended to exercise.
Candidate test A newly generated test that has not yet been accepted or rejected.
Positive test A test that checks behaviour that already works and passes on both the buggy and fixed versions.
Negative test A test that fails on the buggy version because of the selected bug and passes on the fixed version.
Valid test A generated test that has passed all checks required for its type under FR-03.
Repair tool A program, such as PyTER, that uses the buggy code and supplied tests to generate possible fixes.
Developer test suite The collection of tests written by the project's developers, which the user runs manually to evaluate a candidate patch.
Run record The saved information about one workflow run, including its inputs, settings, generated tests, patches, and results.

Test execution outcomes

A test execution has one of these outcomes:

Outcome Meaning
PASS The selected test executed and satisfied its expected behaviour.
FAIL The selected test executed and violated its expected behaviour, through a failed assertion or an unexpected exception from the exercised program.
ERROR The system could not obtain a behavioural result, for example because of a syntax, collection, dependency, or setup error.
TIMEOUT Execution exceeded the configured time limit.
NOT EXECUTED The test was skipped, disabled, not collected, or otherwise did not execute.

A zero process exit code alone does not establish PASS. Expected-failure markers do not turn an unverified result into PASS.
